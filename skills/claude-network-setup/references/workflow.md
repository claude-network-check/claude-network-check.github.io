# 实施与验证

## 基线与配置来源

优先使用已有配置接口和内核 API；没有可用接口时，读取必要文件或使用授权 UI 工具。不要假定某个 CLI、应用路径或操作权限一定存在。

读取客户端与内核版本、订阅和覆写链、模式、TUN、端口、节点类型与链式引用、系统 DNS/代理/路由，以及相关应用的独立代理。只输出必要且脱敏的字段；环境变量中的凭据只显示是否存在。

有其他 VPN 时记录共存约束。只读验证不需要启动付费模型请求或上传用户内容。

模板中 RELAY 是中转，ISP-EXIT 是最终出口。AnyTLS → SOCKS5 是一种实现，不是唯一组合。依用户服务资料和内核支持选择协议，不猜测最快地区。

持久配置可能来自订阅、脚本或覆写。修改前备份并限制备份权限，避免软件把运行中的旧值写回。只改 runtime YAML 不算完成。

使用已安装内核的语法检查功能，例如 `mihomo -t -f <candidate.yaml>`；先确认实际命令与版本。未填写模板不启动、不做公网连接测试。

重载后从内核或客户端确认规则模式、TUN 状态、最终 MATCH 和 dialer-proxy。文件存在不能证明生效。

## DNS 与连接

模板的 DoH 端点使用数字 IP，查询指定经 ISP-EXIT。两个代理 server 也必须填写数字 IP，减少启动递归；TLS SNI 仍按供应商要求填写。

不同内核版本对 DNS 参数支持可能不同，先检查语法，再验证实际查询。不要擅自给未知配置加入 DNS fallback，因为它可能改变查询出口。

监听本机 53 端口可能需要客户端服务权限。确认监听与解析成功后，才把系统 DNS 改为回环地址；记录原值，以便退出客户端时恢复。TUN DNS 劫持覆盖范围需要实测。

浏览器独立 DoH 不遵循系统 nameserver-policy，但请求本身可能仍通过代理。区分解析器位置、DNS 传输路径和真实 IP 泄露。

验证证据包括：

- 内核连接元数据中的 inbound、rule、rulePayload、chains。
- 可信公网 IP 回显服务的实际出口；公开时脱敏。
- 操作系统中代理服务器连接实际使用的网卡。`route get` 可能只显示 TUN 接管路由，不能单独证明内核实际出口。
- 获准直连与默认代理目标各一个，以及新终端的继承效果。

用户要求所有公网探测走代理时，不能先进行无代理 curl 对比。没有足够工具或权限时，明确验证边界。

## 浏览器

macOS Chrome 的应用级策略示例：

```bash
defaults write com.google.Chrome WebRtcIPHandling -string disable_non_proxied_udp
```

执行前备份原值；其他 Chromium 浏览器先确认 bundle ID 和策略支持。不要写入猜测的应用域。

在 `chrome://policy` 重载并检查状态、来源和级别，再检查有效偏好。普通 defaults 可能显示 Recommended，仍可被用户或扩展覆盖，不能称为强制锁定。

该设置限制非代理 UDP，不一定禁用 RTCPeerConnection。扩展可能另行禁用页面 API，不能把二者视为完全相同。

WebRTC ICE 测试设置有限时长，并在结束时关闭连接。零候选也可能来自 STUN 不可达，要结合有效策略解释。测试新 Profile 时不要清空用户登录状态。

只有用户要求时才调整地区、时区和语言。目标地区与使用偏好由用户决定，英文不是必要条件。已有 Profile 的语言修改不保证未来 Profile 继承。

## IPPure 与停止条件

用户指定时，在实际使用的 Profile 打开 https://ippure.com/claude。检查出口、DNS、WebRTC、时区、语言和页面当前展示的分项，使用当时可用的浏览器工具。

不固定算法、分数方向或阈值；以页面说明为准。“约 30 分”只能作为用户的参考目标，不承诺达到。评分不等于服务官方风险判断。

一次改变一类可解释的设置再重测。重测没有新证据，或剩余问题来自 IP 信誉、归属数据库或服务商属性时，停止盲目修改并说明限制。不要为分数关闭 TLS 校验或制造验证结果。

## 回滚与分享

恢复原持久配置后重载。停用本机 DNS 前先恢复原系统 DNS。浏览器只恢复或删除此次修改的键，不删除整个偏好域。已运行进程的环境不会因文件修改自动更新，需新终端或清除已确认的旧变量。

只分享空模板和脱敏说明；凭据、真实 IP、账号、原始日志、截图、备份与本机绝对路径不能进入分享包。
